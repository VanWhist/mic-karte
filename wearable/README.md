# コンディション可視化アプリ v1（wearable）

ウェアラブルから自動収集してスプレッドシートに蓄積しているデータを、
スマートフォンで閲覧するための画面です。

**このアプリの第一の用途は、担当の理学療法士（PT）にレビューしてもらうことです。**
「この画面で練習量の判断ができるか、項目や見せ方に過不足はないか」を
意見してもらうためのたたき台です。

---

## このアプリがしないこと（設計の根幹）

実装を変更するときは、必ず先にこの5つを読んでください。
実装の都合でここを曲げると、アプリの意味がなくなります。

1. **「練習を止める・減らす」判断の材料としてのみ使う。**
   数値が良好であることを「進んでよい」の根拠には絶対にしない。
2. **総合スコア・Readiness・コンディション点数のたぐいを作らない。**
   複数指標を1つの数字に丸めない。
3. **健康状態の表示に緑色を使わない。**
   緑は一般的なUIで「成功・完了」を意味するため、「今日は練習してよい」という許可に読まれる。
4. **「正常」「良好」「問題なし」という語を使わない。**
   平常時の文言は「目立つ変化は検出されていません」。
5. **アプリは観察事実だけを書く。判断は書かない。**

あわせて次の2つも仕様です。

- **個人基準（ベースライン）を自動更新しない。**
  自動更新すると、徐々に悪化した状態まで「新しい平常」として吸収してしまい、
  悪化が検出できなくなる。復帰期の選手では特に危険。
- **絶対値の閾値を書かない。**
  AppleヘルスケアのHRVは原則 SDNN、スポーツ分野で広く使われる7日平均の研究は LnRMSSD で、
  指標の種類が違うため、文献の閾値をそのまま当てはめてはいけない。
  判定は「個人基準比（%）」と「基準期間の標準偏差に対する逸脱（SD）」だけで行う。

## ファイル構成

| ファイル | 中身 |
|---|---|
| `index.html` | フロントエンド。単一ファイル、CSS/JSインライン、外部CDN・チャートライブラリなし。グラフは手書きのインラインSVG |
| `read_api.gs` | 既存のApps Scriptに追加する読み取り専用API（`action=summary` の分岐） |
| `screenshots/` | 390px幅での表示確認用スクリーンショット |
| `README.md` | このファイル |

判定の閾値は `index.html` の **`RULES` オブジェクト1箇所** にまとめてあります。
同じ内容は画面下部の「この画面の判定の作り方」にも日本語で表示しているので、
PTからの指摘は `RULES` を直すだけで画面全体に反映されます。

## データソース

Googleスプレッドシート「MICコンディション管理」の **`wearable` シートのみ** を読みます。1日1行。

`morning` シート（朝の主観入力：膝の腫れ・痛み・こわばり）と
`session` シート（練習後入力：RPE・ジャンプ本数）は**まだ存在しません。参照していません。**

ただし指標の優先順位は
**「膝など局所の翌朝の反応 ＞ 睡眠 ＞ 安静時心拍・HRV」** であり、最優先はこの未実装の2つです。
そのため画面最上部に、この2つを「未実装」と明示したグレーの枠として置いてあります。
**枠を置くこと自体が優先順位を伝える手段なので、省略しないでください。**

### 欠測の扱い

- 空欄は普通にあります。デバイス未装着の日、同期漏れの日は行ごと存在しないこともあります。
- **欠測を0として扱いません。** グラフでは点線の枠として描き、平均・標準偏差の計算から除外します。
- `wrist_temp`（手首皮膚温）は現在のデバイスでは取得できないため常に空です。

## セットアップ手順

### 1. スクリプトプロパティを設定する

Apps Scriptプロジェクト「ウェアラブル取り込み用」
（スクリプトID `1FcftU72wx3PO4HcIxm0He1Z-VHKEU_Sb_DMeDriC0TfB9oz1nk4ANr37`）を開き、
**プロジェクトの設定 → スクリプト プロパティ** に次の2つを追加します。

| プロパティ名 | 値 |
|---|---|
| `VIEW_TOKEN` | 閲覧用のトークン（自分で決めた十分に長いランダム文字列） |
| `VIEW_BASELINE_JSON` | 個人基準の期間設定（下記のJSON） |

> **取り込み用の `INGEST_KEY` は流用しないでください。**
> 用途（書き込み／読み取り）と配る相手が違うため、別のトークンを新設します。
>
> **トークンの実物の値を、コード・README・コミットメッセージ・チャットのどこにも書かないでください。**
> スクリプトプロパティにだけ入れます。

`VIEW_BASELINE_JSON` の値（`start` / `end` は実際の基準期間に置き換える）:

```json
{
  "van-test": {
    "name": "van（テスト）",
    "start": "2026-07-28",
    "end": "2026-08-03",
    "approved_by": "担当PT",
    "approved_at": "2026-08-04"
  }
}
```

トークン文字列の作り方の一例（生成した値はプロパティ欄に直接貼り、ファイルに保存しない）:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

### 2. `read_api.gs` を追加する

同じプロジェクトに **新規ファイルとして** `read_api.gs` を追加し、内容を貼り付けます。

**新しいApps Scriptプロジェクトを作らないでください。**
Apps Scriptはプロジェクト内の全ファイルがグローバル名前空間を共有するため、
別ファイルに `doGet` / `doPost` を作ると、
**エラーが出ないまま既存の取り込みアプリが壊れます。**

`read_api.gs` には `doGet` / `doPost` を定義していません。
このファイルが作るグローバル名はすべて `view` で始まります
（`VIEW_CFG` / `VIEW_COLUMNS` / `viewSummary_` ほか）。
既存コードに同名のものが無いことだけ確認してください。

### 3. 既存の `doGet` に1行足す

既存の `doGet` の**先頭**に、`action=summary` の分岐を足します。既存の分岐は消しません。

```javascript
function doGet(e) {
  var p = (e && e.parameter) || {};                      // ← 既存に無ければ足す
  if (p.action === 'summary') return viewSummary_(p);    // ← この1行を足す

  // ── ここから下は既存のコードをそのまま残す ──
  ...
}
```

既存の `doGet` が `e.parameter` を別の変数名で受けている場合は、その変数名を使ってください。

### 4. 動作確認（デプロイ前）

エディタで `viewSelfTest` を選んで実行し、実行ログを見ます。
トークンの値そのものはログに出しません。

確認する内容:

- `VIEW_TOKEN 設定: あり`
- `VIEW_BASELINE_JSON 設定: あり`
- `シート「wearable」: あり（N行）`
- `ok: true` ／ `取得件数: N 日分`
- **`date の型: string`** ← ここが `object` になっていたら日付がDate型に化けています

### 5. ウェブアプリとして再デプロイする

**デプロイ → デプロイを管理 → 既存のデプロイを編集 → バージョン「新バージョン」→ デプロイ**

- 次のユーザーとして実行：**自分**
- アクセスできるユーザー：**全員**

> 「新しいデプロイ」ではなく**既存デプロイの編集**にしてください。
> 新規デプロイにすると `/exec` のURLが変わり、既存の取り込み側の設定が動かなくなります。

### 6. フロントエンドの接続先を設定する

`index.html` の先頭付近にある `CFG.API_URL` を、上記デプロイの `/exec` URL に書き換えます。

```javascript
var CFG = {
  API_URL: "https://script.google.com/macros/s/＜デプロイID＞/exec",
  DEFAULT_ATHLETE: "van-test"
};
```

`CFG` にトークンは書きません。トークンは閲覧者に渡すURLのクエリパラメータで渡します。

### 7. GitHub Pages に配置する

このディレクトリごと、既存リポジトリ `vanwhist/mic-karte` に `wearable/` として置きます。

```bash
git add wearable
git commit -m "ウェアラブルのコンディション可視化アプリ（v1・PTレビュー用）を追加"
git push
```

公開URL:

```
https://vanwhist.github.io/mic-karte/wearable/
```

## 使い方

### 閲覧者に渡すURL

```
https://vanwhist.github.io/mic-karte/wearable/?token=＜VIEW_TOKENの値＞&athlete=van-test
```

- ログイン機構はありません。URLを知っている人が見られます。閲覧者3名にだけ渡してください。
- 読み取り専用です。この画面からシートに書き込むことはできません。
- **URLはメッセージアプリなどに貼ると転送されます。渡す相手を絞ってください。**

### サンプルデータでの表示（トークン不要）

`token` を付けずに開くと、サンプルデータで表示します。PTに見せるたたき台用です。
画面上部のセレクタで状態を切り替えられます。

| URL | 状態 |
|---|---|
| `?demo=full` | データが十分にある状態 |
| `?demo=attention` | 「確認が必要」が出ている状態 |
| `?demo=consult` | 「PTへ確認」が出ている状態 |
| `?demo=sparse` | データ不足の状態 |
| `?demo=single` | 1日分だけ |
| `?demo=empty` | 0件 |

## 動作確認の手順

ローカルで確認する場合は、`file://` ではなくHTTPで開いてください。

```bash
python -m http.server 8777 --directory mic-karte
```

`http://localhost:8777/wearable/index.html?demo=full` を開き、次を確認します。

- [ ] 390px幅で横スクロールが出ない
- [ ] 最上部の固定文言（練習の許可を判定する画面ではない旨）が見えている
- [ ] 「膝の翌朝反応」「前日の負荷」が未実装カードとして最上部に並んでいる
- [ ] 健康状態の表示に緑が使われていない
- [ ] 「正常」「良好」「問題なし」が出ていない
- [ ] `?demo=sparse` `?demo=single` `?demo=empty` で画面が壊れない
- [ ] 欠測日がグラフで点線になっている（0の棒になっていない）
- [ ] アコーディオンが閉じた状態でも各見出しに一行要約が出ている

実データでの確認:

- [ ] `?token=...&athlete=van-test` でデータが表示される
- [ ] 間違ったトークンで「アクセストークンが正しくありません」が出る
- [ ] 「基準期間」が画面に表示されている

## v1で意図的にやっていないこと

| 項目 | 理由 |
|---|---|
| 膝の翌朝反応・前日の負荷（RPE・ジャンプ本数）の表示 | 入力の仕組み（`morning` / `session` シート）が未実装。**最優先項目なので、枠だけ置いて明示している** |
| PTコメントの書き込み | v1は読み取り専用。書けるようにするかはPTと相談して決める |
| ログイン機構 | 閲覧者3名。URLトークンで足りる |
| 複数選手の切り替えUI | 現在データがあるのはテスト用の1人だけ。`athlete` パラメータで切り替えられる |
| 個人基準の自動更新 | **仕様として実装しない**（上記「このアプリがしないこと」参照） |

## PTに確認したいこと

画面下部にも同じ内容を載せています。

1. この画面で「練習量を減らす・止める」判断ができるか。項目に過不足はないか
2. 「確認が必要」を出す条件（現在は個人基準比と標準偏差ベース、数値はすべて暫定）が妥当か
3. 基準期間が短い／安定しすぎているとSDが小さく出るため、わずかな変化でも「確認が必要」が立ちやすくなります。
   逆に厳しくすると見落とします。**どちらに寄せるべきか**
4. 「膝の翌朝反応」「前日の負荷」を、誰が・いつ・どの尺度で入力するか
5. 個人基準の期間をどう決め、どのタイミングで更新するか
